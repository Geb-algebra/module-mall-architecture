# Module Mall Architecture

## 適用範囲

Module Mall Architecture（MMA）は、コードベースを境界で区切られた複数のPackageとして理解できる場合に適用する。Packageは、責務、公開範囲、依存関係を持つソースコードの論理的な集合を指す。Packageはデプロイ単位、実行プロセス、リポジトリ、特定のパッケージマネージャーの単位と一致しなくてよい。

このContextは、設計、実装、変更、レビュー、テスト設計、不具合調査、説明でPackage境界と依存関係を判断するときに利用できる。このContext自体は、それらの活動の目的、手順、成果物、完了条件、報告形式を定めない。

言語、フレームワーク、ビルドシステム、manifest、公開entrypointの具体的な表現方法は対象外とする。それらの規約は、適用環境に対応する別のContextから得る。

## 用語

| 用語 | 意味 |
|---|---|
| 変更要求（Change Requirement） | コードの変更箇所や変更方法を指定せず、システムの挙動または設計に必要な変更を表したもの。 |
| 影響範囲（Scope） | 変更要求に対応する活動で、変更、確認、テスト、または影響可能性の検討が必要なコードベースの範囲。 |
| Package | 何らかの境界で区切られたソースコードの集合。 |
| 公開契約（Public Contract） | 外部Packageが依存してよい公開APIと、その入力条件、保証される振る舞い、エラー、副作用などの約束。 |
| 公開契約資料（Public Contract Artifact） | 公開契約を内部実装より短時間かつ少ない情報量で理解できる、信頼可能な資料。 |
| 内部実装（Internal Implementation） | 公開契約を実現するコードのうち、外部に維持を約束しない部分。 |

## 影響範囲の因果モデル

変更要求の影響範囲は、次の二種類のPackageから成る。

1. 変更要求へ直接対応するPackage
2. 直接対応するPackageまたはその依存先の変更によって、変更、確認、テストが必要になりうるPackage

影響範囲を小さく保つには、直接対応するPackageの数と大きさ、および変更の影響を受けるPackageの数を抑える必要がある。影響範囲を特定しやすくするには、変更要求とPackageの対応、およびPackage間の影響経路を、内部実装の広い探索なしに判断できる必要がある。

この因果関係から、Package設計には次の四条件が生じる。

- 一つの変更要求に直接対応するPackageが少なく、各Packageが必要以上に大きくない。
- 一つのPackageの変更から影響を受けるPackageが少ない。
- Packageが変更要求に対応するかを、内部実装を広く読まずに判断できる。
- 変更対象の公開契約を利用する他Packageと、そこからの間接的な影響候補を追跡できる。

四条件を支える性質が、変更凝集性、実装隠蔽性、ブラックボックス性、依存追跡性である。

## 変更凝集性（Change Cohesion）

変更凝集性は、Packageを技術的な種類ではなく変更理由に沿って分割する性質である。変更理由とは、コードを変化させる独立したルールまたは関心事を指す。

### 不変条件

- **CC-01 単一所有**: 一つのルールまたは判断の正本を、一つのPackageが所有している。同じルールを複数Packageが重複して定義していない。
- **CC-02 同一理由の集約**: 同じ変更理由で変わるコードが、その理由を所有するPackageへ集まっている。他Packageは所有Packageの公開契約を通じて利用している。
- **CC-03 独立理由の分離**: 互いに独立して変わる理由を、便宜的な共有Packageや技術分類だけを理由に一つのPackageへ混在させていない。
- **CC-04 変更理由の説明可能性**: 各Packageについて「何が変わるときに変わるか」と「何が変わっても変わらないか」を一貫して説明できる。

公開契約の変更へ利用側が追従することは、ルール所有の分散ではない。一つの変更要求が独立した複数の変更理由を含む場合は、それぞれの所有Packageが直接対応してよい。

### 例

- **準拠**: 期限切れ判定を所有するPackageと、その表示方法を所有するPackageを分け、判定ルールを前者だけに定義する。
- **違反**: `utils`、`logic`、`ui`という技術分類へ同じ期限切れルールを分散させ、ルール変更のたびに三つすべてを直接変更する。

## 実装隠蔽性（Implementation Hiding）

実装隠蔽性は、Packageを最小限の公開契約と内部実装へ分け、外部Packageが内部実装へ依存できない性質である。外部が依存できる面を限定すると、公開契約を維持する内部変更の影響を所有Package内へ閉じ込められる。

### 不変条件

- **IH-01 境界経由**: 外部Packageからの利用は、所有Packageが公開契約として明示した境界だけを経由する。
- **IH-02 内部依存の禁止**: 外部Packageから、内部ファイル、内部データ構造、内部エラー、アルゴリズムなど維持を約束しない実装詳細へ依存できない。
- **IH-03 公開面の最小性**: 公開契約には外部利用に必要な要素だけが含まれ、便宜のために内部構造を一括公開していない。
- **IH-04 変更の局所性**: 公開契約を維持した内部変更だけを理由として、外部Packageの変更を必要としない。

### 例

- **準拠**: 外部Packageは明示された生成操作を利用し、所有Packageが内部の永続化形式を変えても影響を受けない。
- **違反**: 外部Packageが所有Packageの内部mapperを直接利用し、内部データ構造の変更だけで外部も修正を要する。

## ブラックボックス性（Black Box Usability）

ブラックボックス性は、内部実装を読まず、公開契約と公開契約資料だけでPackageの責務、利用可否、期待される振る舞いを判断できる性質である。

### 不変条件

- **BB-01 責務の可視性**: 公開契約資料から、Packageの責務、非責務、変更理由を判別できる。
- **BB-02 振る舞いの可視性**: 公開APIの意味、入力、前提条件、保証、エラー、副作用など、外部から観測可能な約束を公開契約資料から把握できる。
- **BB-03 探索の局所性**: 公開契約に必要な情報が一か所、または明確にたどれる少数の資料へ整理され、内部実装より十分に小さい。
- **BB-04 現在性**: 公開契約資料が現在の公開契約を表し、公開契約の変更とともに更新されている。
- **BB-05 要求との対応可能性**: 変更要求がPackageの責務に関係するかを、候補Packageの内部実装を読む前に公開契約資料から判断できる。

### 例

- **準拠**: Packageの責務と外部から観測可能な失敗条件が短い公開契約資料にまとまり、要求との関係をそこから判定できる。
- **違反**: 公開関数名だけでは責務や副作用が分からず、利用可否を判断するために全実装と内部テストを読む必要がある。

## 依存追跡性（Dependency Traceability）

依存追跡性は、Package間の意味上の依存を明示し、直接および間接の影響候補を静的または明確な記録から追跡できる性質である。

### 不変条件

- **DT-01 直接依存の明示**: すべてのPackageについて、どの他Packageの公開契約へ直接依存しているかが明示され、Package単位の依存グラフを構成できる。
- **DT-02 宣言と実態の一致**: 明示された依存と実際の利用が一致し、未宣言の依存や境界を迂回した依存が存在しない。
- **DT-03 意味上の依存の可視性**: イベント、設定、データ形式、命名規則、共有資源などを介する依存も、影響追跡に必要な関係として観測できる。
- **DT-04 解析可能な結合**: 可能な依存は型、関数、クラス、定数、schemaなどの参照可能なシンボルを介し、参照検索や静的検査から利用箇所を特定できる。
- **DT-05 非シンボル依存の記録**: シンボルで表現できない依存は、依存元、依存先、対象の契約または資源、依存理由を明記している。
- **DT-06 影響外縁の追跡可能性**: 公開契約の変更から直接依存するPackageを列挙でき、必要に応じて依存グラフを再帰的にたどって間接的な影響候補の外縁を判断できる。

### 例

- **準拠**: イベントの名前とデータ形式を所有Packageの公開契約として一度だけ定義し、発行側と購読側が同じ定義を参照する。
- **違反**: 発行側と購読側が同じ文字列とデータ形式を別々に記述し、両者の意味上の依存を参照検索や依存グラフから発見できない。

## 四つの性質の関係

| 性質 | 主に抑えるもの | 主に可能にする判断 |
|---|---|---|
| 変更凝集性 | 変更要求へ直接対応するPackage数と各Packageの大きさ | どのPackageが変更理由を所有するか |
| 実装隠蔽性 | 内部変更が外部へ伝播する機会 | 公開契約を維持した変更をPackage内へ限定できるか |
| ブラックボックス性 | 要求とPackageの対応を調べる探索量 | 内部実装を読む前に変更対象候補を選べるか |
| 依存追跡性 | 公開契約変更の影響先を探す探索量 | 直接・間接の影響候補を依存関係からたどれるか |

一つの性質を別の性質で代替しない。例えば、実装を隠しても公開契約の意味が不明ならブラックボックス性は成立せず、依存を宣言しても未宣言の迂回経路があれば依存追跡性は成立しない。

## トレードオフの扱い

実行環境、性能、セキュリティ、法令、チームの責任分担など、より優先度の高い制約が四つの性質の一部を弱める場合がある。その状態は、次のすべてを観測できる場合に限り、意図的なトレードオフとして区別できる。

- 優先した制約と、通常の規則を満たせない理由が明記されている。
- 分散した変更理由、露出した実装、暗黙的な依存など、残る影響経路と所有者が特定できる。
- 例外が適用されるPackageと契約の範囲が限定されている。

記録されていない例外、影響経路を追えない例外、他の重要な性質を損なわず解消できる逸脱は、意図的なトレードオフではなく対応する不変条件への違反である。
